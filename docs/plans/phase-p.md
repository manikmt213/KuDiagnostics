# Phase P — admin UI and docs (started 2026-11-21)

From `docs/plans/ecosystem-spec-gap.md` (row 13; spec 20, 20.2–20.3, 21, 25.3, 25.11): an Integrations tab, the consent wording "Full Site Administration", connection activity with a high-risk filter, per-integration docs generated from the catalogue, and an adapter developer guide. Exit gate: the screens checked in a browser.

## What exists (read 2026-11-21)

- Tools > KuDiagnostics (`Admin\ConnectionsPage`): connector URL, active connections (app, user for managers, raw scope string, expiry, revoke), read-only switch (D80), hide UI (D23), last 20 tool calls. Hidden mode removes the page (presentation only, rule 7).
- Consent form (`OAuth\Authorize::consent()`): one line per scope; `kuduy:admin` reads "Manage plugins, themes, users and settings".
- Audit table `kuduy_audit_log`: ts, user, client, tool, redacted args, result, error code, duration, object type/id, snapshot id (indexes on ts, tool+ts, user+ts).
- `kuduy-integrations` builds each catalogue row's state (installed, active, version, support, tools available); `docs/TOOLS.md` is generated by `scripts/tool-reference.mjs` from the registry inside Playground.

## Decisions

| # | Decision | Choice |
|---|---|---|
| D84 | Admin screen | Three tabs on the existing Tools page (`?tab=`): **Connections** (each connection's access in words, last use, calls in the last 7 days, link to its activity, revoke; then read-only mode and hide UI as now), **Activity** (audit rows, 50 a page, filters: connection, result, high-risk only; users see their own rows, site managers everyone's), **Integrations** (for users who can `activate_plugins`: the same data as `kuduy-integrations` — installed by default, all on request — with the last time Claude ran an integration check). High-risk = tools that are confirm-first, destructive, or need `kuduy:admin` / `kuduy:code`, taken from the registry. No new tables or options; hidden mode still removes the whole page. |
| D85 | Scope wording | One source of labels and explanations (`Scopes::label()`, `Scopes::explain()`) for the consent form and the admin page: read "Read content and settings", write "Create and edit content", admin **"Full Site Administration"** with what it adds (plugins, themes, users, settings, site templates, permanent deletes — still limited by the user's own WordPress permissions, risky actions ask first), code "Run code (developer mode)" explained on its own line and offered only when the site owner switched it on. Wording only: what each scope allows does not change. |
| D86 | Generated integration docs | `scripts/tool-reference.mjs` also writes `docs/INTEGRATIONS.md` from `IntegrationCatalog::all()` in the same Playground run: per category, each product's support class, free or paid, the tools behind it (count and prefixes) and the catalogue note. `docs/DEVELOPER.md` gets "Writing an adapter": tool contract, catalogue row, snapshots, confirm-first, plugin APIs only, tests (real plugin or stand-in), regenerating the docs. |

## Tests

`AdminScreensTest` (AP1–AP4): AP1 tabs render for an administrator, the author sees Connections and Activity but not Integrations; AP2 connections show access in words and last use; AP3 activity filters (connection, result, high-risk only) and an author sees only their own rows; AP4 integrations tab lists installed rows by default and the whole catalogue with `all`. AP5 in `OAuthTest`: the consent form shows "Full Site Administration" and explains code access separately. Browser check of the three tabs on the owner's test site (exit gate; the owner asked for the live site instead of a Playground site); the consent form is covered by AP5 only.
